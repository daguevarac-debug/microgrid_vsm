# BAT26-33 — puente BLAST-Lite y capacidad por ventanas

## Alcance

`bess.blast_lite_adapter.BlastLiteAdapter` opera fuera de `solve_ivp`: un proceso Python 3.12.10 conserva una instancia de la clase original BLAST-Lite 1.1.0; el proceso Python principal intercambia ventanas por JSON y recibe un `CapacitySnapshot` inmutable. El worker comprueba versión y hashes auditados de la clase y la base frente al commit `b093495b47dc40dd96dba865d91f553619501e94`. Si falta el ejecutable, paquete o coincide mal la versión, informa error; no hay sustitución manual. La ruta lineal no importa BLAST ni crea proceso. Usar el adaptador como context manager para cerrar el proceso.

El `q0` se fija al crear el adaptador. `anchor_case()` permite fijar explícitamente un nuevo inicio de escenario tras una historia previa sin reiniciar BLAST, resetear EFC ni borrar la última frontera. Es un inicio de caso distinto: la capacidad inicial del caso se fija al valor configurado y `q/q0=1`. No debe usarse para borrar degradación de un mismo caso. `history` registra el ancla, tiempo, número de muestras, SHA-256 del perfil sintético y resultados; el consumidor debe conservar el perfil original además del hash. El historial de BLAST vive solo mientras exista el proceso; no hay recuperación tras cierre o fallo ni checkpoint durable.

`q_init_case_ah=44.1` por defecto y `CapacitySnapshot(66, q_init, q/q0)` aplica retención una sola vez. 43.5 Ah es otro caso. El worker comprueba `cap=66`, `cap_2ndLife=46` y `qNew(0)=0.7` (46.2 Ah al multiplicar por 66), sin reconciliar 46 y 46.2 Ah. `qNew` se reporta como dato BLAST y no se aplica a la capacidad del caso. La transferencia a 44.1 o 43.5 Ah sigue siendo hipótesis, no una validación física.

Para cada ventana se exige tiempo creciente, SoC, temperatura y corriente 2p alineados, unidades y signo explícitos, y coincidencia exacta de tiempo, SoC fraccional y temperatura en el punto compartido con la anterior. La corriente 2p solo se exige para trazabilidad y hash: BLAST original recibe tiempo, SoC y temperatura, y calcula EFC internamente. No se deduce corriente 2p de la corriente del bus y no se demuestra consistencia I–SoC. El adaptador rechaza perfiles operativos: solo acepta señales expresamente `synthetic`, `synthetic_cell` y `synthetic_2p_group`; no suministra temperatura ni corriente por defecto. La etiqueta sintética no valida físicamente el perfil.

La frontera de capacidad sigue ADR-001: se entrega un snapshot para la siguiente ventana rápida y el llamador conserva sin modificar el vector de estados, incluido SoC fraccional, `Vrc`, `z_deg`, estado del controlador y PI. El cambio de snapshot no es corriente, potencia, energía intercambiada, throughput ni EFC. La expresión `SoC*Q_eff` no se conserva automáticamente, y la hipótesis no está validada físicamente. El adaptador rechaza snapshots inferiores al SoH mínimo configurado; el modelo comprueba también sus propios límites. No hay clipping de SoC. `R0(SoH)` permanece tal como estaba y no se valida al recibir SoH de BLAST.

## Selección de modo y compatibilidad

`MicrogridWithBESS(..., aging_mode='linear')` exige ausencia de snapshot y utiliza la ley histórica de `z_deg`. `aging_mode='blast'` exige snapshot y utiliza su SoH/Qeff fijo durante esa instancia/ventana: `z_deg` sigue evolucionando como diagnóstico, pero no resta pérdida lineal adicional. Ambos son excluyentes. **Actualización BAT26-39:** omitir `aging_mode` selecciona `linear`; el snapshot requiere `aging_mode='blast'` y `blast_profile_kind='synthetic'`. La interfaz provisional anterior aceptaba ese snapshot implícitamente; sus llamadores deben añadir ambas declaraciones. La etiqueta es una declaración del llamador: el constructor no certifica el origen de un snapshot construido manualmente ni habilita operación física. El adaptador BLAST comprueba sus entradas y bloquea perfiles operativos.

Para la ventana siguiente se debe construir la instancia de microrred con el nuevo snapshot y pasarle como condición inicial final de la ventana anterior el vector completo sin rebase. `preserve_window_state` devuelve una copia del vector de 15 o 16 estados y rechaza SoC fuera de los límites indicados, sin recortarlo; su uso por el llamador es explícito. El llamador es responsable de que ninguna actualización ocurra dentro de una integración en curso. No se cambian ni el ECM, ni el convertidor, ni las ecuaciones VSG/LCL/DC, ni los 12/15/16 estados. No se incorporó un orquestador automático de ventanas.

## Validación y pendientes

Las pruebas `test_blast_lite_adapter.py` usan perfiles sintéticos y el BLAST real del entorno aislado. Comprueban referencia/capacidad inicial, historial, ancla posterior a historial previo, exclusividad, continuidad y frontera sin corriente/potencia/throughput/EFC, límites SoC, dependencia ausente, perfiles operativos rechazados y rechazo transaccional bajo límite SoH. Los ejemplos no constituyen prueba de conservación energética integral ni validación experimental.

El modelo cíclico de BLAST tiene soporte declarado alrededor de 25 °C, DoD 100 % y 1C. Las campañas FV requieren datos de grupos 2p, temperatura de celda, corriente, SoC, procedencia, topología y escalamiento; no hay perfil operativo acreditado aquí. El estudio anterior observó sensibilidad al tamaño de ventana y no demostró convergencia; este puente no fija una tolerancia ni extrapola los resultados. Queda pendiente instrumentar persistencia duradera y recuperación, validez física de `R0(SoH)`, una política de perfiles acreditados y sus criterios, el acoplamiento temporal completo y su prueba con trazas físicas. BAT26-33 sigue abierta.
